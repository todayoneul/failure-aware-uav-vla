# CARLA-Air 확인 기록

이 문서는 [연구 계획](research_plan.md) 7.1절의 CARLA-Air 확인 결과를 적는다. 2026-11-23에 했다.

**결론: 본 실험에는 쓰지 않는다.**

- 필수 항목 2(동기 모드에서 드론 물리가 `world.tick()`을 따라감)가 실패했다.
- 계획에 정한 대로, 지금의 CARLA 0.9.16을 유지한다.
- 드론은 자체 동역학 모델로 움직인다(4절).

경로는 `car_follow/` 기준이다.

## 1. 대상과 환경

- **빌드.** CARLA-Air v0.1.7 Windows 빌드(CARLA 0.9.16 + AirSim 1.8.1, Unreal Engine 4.26)다.
  - GitHub release에서 4조각(합계 6.69GB)을 받았다. 조각과 합친 zip의 SHA256이 공개 값과 모두 같았다.
  - `assets/carla-air-v0.1.7/`에 풀었다(31,888개 파일, 16.4GB).
- **실행.** 함께 든 시작 스크립트(`CarlaAir.ps1`)는 읽기만 하고 쓰지 않았다. 그 스크립트는 모든 CARLA 프로세스를 끄고, 차 30대와 보행자 50명을 자동으로 띄우기 때문이다.
  - 대신 `WindowsNoEditor/CarlaUE4.exe`를 직접 실행했다. 인자는 `Town05 -windowed -ResX=640 -ResY=360 -quality-level=Low -nosound -unattended`이다.
  - CARLA 포트(2000)와 AirSim 포트(41451)는 둘 다 8초 만에 열렸다.
- **AirSim 설정.** 함께 든 `AirSimConfig/settings.json`을 바꾸지 않고 `%USERPROFILE%\Documents\AirSim\settings.json`에 복사했다. 이 폴더는 원래 없었다.
  - 설정 내용: SimpleFlight 드론 하나, 1280×960 카메라 두 대.
- **Python 환경.** 함께 든 carla wheel은 Python 3.10용(`cp310`)뿐이다. 그래서 별도의 Python 3.10 환경을 uv로 만들었다.
  - 설치한 것: 그 wheel, `airsim` 1.8.1, `msgpack-rpc-python`(tornado 4.5.3).
  - 우리 uv 환경(Python 3.12)은 건드리지 않았다. 확인용 환경은 임시 폴더에 두었다.
  - Python 3.12에서도 `airsim`을 import할 수는 있다. 다만 `backports.ssl_match_hostname`이 더 필요하다. 3.12에서 `ssl.match_hostname`이 없어졌기 때문이다.
- **스크립트.** `scripts/carla_air/`의 probe 네 개다. 결과는 `outputs/carla_air_check/`(로컬)에 저장된다.

```powershell
python -I scripts/carla_air/probe1_connect_sync.py   # 위의 Python 3.10 환경에서, simulator를 켠 뒤
```

### 2.1 client 연결

- **PyPI carla 0.9.16.** 우리 uv 환경에 깔린 client다. 연결은 됐지만 경고가 나왔다.
  - 경고 내용: client 버전은 `0.9.16`, simulator 버전은 `7a7fdb3-dirty`로 다르다.
  - 그 직후 `LibCarla/source/carla/sensor/data/Array.h` 132행의 크기 검사 assertion으로 프로세스가 멈췄다.
  - 원인 추정: client가 접속 때 받는 월드 상태 stream의 구조가 CARLA-Air에서 바뀌어 binary 수준에서 맞지 않는다.
  - 근거: CARLA-Air의 환경 설치 스크립트도 PyPI carla를 지우고 자체 wheel을 깐다.
- **함께 든 wheel.** 연결과 조회가 정상이었다.
  - 드론은 CARLA 쪽에서 `airsim.drone` actor 하나로 보인다.
  - AirSim 좌표와 CARLA 좌표의 차이는 Town10HD에서 (+172.20, −183.86, +27.45)m였다. AirSim은 z가 아래로 양수다. CARLA-Air 문서의 값과 같다.
- **뜻.** CARLA-Air를 쓰려면 Phase 2 환경 전체를 Python 3.10과 이 wheel로 옮겨야 한다.

### 2.2 동기 모드

CARLA를 동기 모드 20Hz(tick당 0.05초)로 두고, 드론에 앞으로 5m/s 속도 명령을 준 뒤 두 가지를 쟀다.

**표 2. tick과 드론 움직임**

| 시험 | AirSim 드론 이동 | AirSim 시계 | CARLA의 드론 actor 이동 |
|---|---|---|---|
| tick 없이 실제 시간 3초 | 10.94m | +3.003초 | 0m |
| tick 60번(시뮬레이션 3초)을 실제 시간 0.92초에 | 4.54m | +0.933초 | 15.39m (첫 tick에 10.94m, 이후 tick당 0.073m) |

- **해석.** 드론 비행 물리는 `world.tick()`과 상관없이 실제 시간으로 돈다. CARLA는 tick마다 그 순간의 드론 위치를 복사해 올 뿐이다.
  - 그래서 tick 간격이 0.05초여도 드론은 tick 사이의 실제 시간만큼 움직인다. 위 시험에서는 tick당 0.073m였고, 0.05초라면 0.25m여야 한다.
- **맞추기 시도.** AirSim의 `simPause(True)`는 드론을 멈췄다(2초 동안 이동 0m, 시계 0초).
  - 하지만 Unreal 게임 전체를 멈추므로, CARLA의 `world.tick()`이 10초 제한을 넘겨 실패했다.
  - 이어서 부른 `simContinueForTime(0.05)`도 시간 초과로 실패했다.
  - 따라서 pause로 tick마다 맞추는 방법은 쓸 수 없다.
- **이것이 중요한 이유.** 연구 계획의 평가는 같은 시험이 똑같이 재현된다는 전제에 선다.
  - 이 전제를 쓰는 곳: 봉인 본평가, `t_fail` 자동 라벨, 보정 목록.
  - 동기 모드가 아니면 차의 움직임과 드론 물리가 실제 시간에 묶인다. 그러면 인식 모델의 계산 시간이 비행 결과를 바꾼다.

### 2.4 속도 명령 응답 (실제 시간, 비동기)

항목 2가 실패했으므로 비동기 모드에서 쟀다. 높이 약 60m에서 SimpleFlight 기본 설정으로 쟀다.

명령은 차례로 이어서 주었다. 그래서 각 명령의 시작 속도는 앞 명령이 끝난 속도다.

**표 3. 계단 응답**

| 명령 속도 | 시작 속도 | 잰 시간 | 끝 속도 | 최대 가속도 | 1차 지연으로 맞춘 시간 상수 |
|---|---|---|---|---|---|
| 10m/s | 0 (정지 비행) | 5초 | 6.64m/s | 2.7m/s² | 4.2초 (처음 0.47초는 반응 지연) |
| 0 | 6.64m/s | 5초 | 1.87m/s | 2.6m/s² | 3.9초 |
| −20m/s | +1.87m/s | 7초 | −13.7m/s | 5.7m/s² | 방향 전환이 섞여 맞추지 않음 |
| 0 | −13.7m/s | 6초 | −2.76m/s | 6.0m/s² | 3.7초 |
| 회전 60°/s | 0 | 3.5초 | 59.7°/s | | 0.02초 안에 30°/s 넘음 |

- **해석.** 속도는 시간 상수 약 4초(3.7–4.2초)의 1차 지연처럼 따라간다. 가속도는 속도 오차에 비례해 커지고 따로 한도가 보이지 않는다(오차 10m/s에서 2.7m/s², 약 22m/s에서 5.7m/s²). 방향 회전은 거의 바로 따라간다.
  - 이것은 SimpleFlight 기본 제어 이득의 성질이고, 쿼드로터 자체의 성질이 아니다.
  - Phase 1의 Project AirSim 드론도 속도 명령을 약 2.4초 늦게 따랐다(`landing_vla/docs/arbitrary_start_generalized_landing.md`).
- **뜻.** 첫 데모 계획의 가정(가속도 4m/s², 최고 20m/s)보다 훨씬 느리다. 이 값을 그대로 자체 동역학 모델의 parameter로 쓰지 않는다(4절).

### 2.5 지도와 자원

- **지도.** 실행 인자의 `Town05`는 무시되고 Town10HD가 떴다.
  - client에서 `load_world("Town05")`를 부르면 6.7초 만에 Town05가 떴고, 드론 actor도 남았다.
  - 좌표 차이는 (+2.60, +2.00, +3.67)m로 바뀌었다. 지도를 바꿀 때마다 다시 재야 한다.
- **GPU 메모리.** 켜기 전 GPU 전체 사용량은 2.0GB였다.
  - Town10HD Low에서 켠 직후 5.6GB였다(simulator 약 3.6GB, AirSim 카메라 포함).
  - Town05로 바꾼 뒤 4.3GB였다(약 2.3GB). 지금의 CARLA와 비슷하다([setup](setup.md)).
- **속도.** 비동기 모드에서 드론을 띄운 채 월드가 초당 60 frame 돌았다.

## 3. 판정

- **규칙.** 연구 계획 7.1절의 규칙은 "필수 항목 1–3이 모두 통과하면 쓴다"이다. 항목 2가 실패했으므로 본 실험에는 쓰지 않는다.
- **검토한 대안: CARLA-Air를 비동기(실제 시간)로 쓰기.** 실제 비행 모델을 쓸 수 있다는 장점이 있지만, 다음 이유로 고르지 않았다.
  1. 시험이 재현되지 않는다. Traffic Manager와 드론 물리가 둘 다 실제 시간에 묶인다.
  2. 인식 모델의 계산 시간과 GPU 부하가 비행 결과를 바꾼다.
  3. 함께 든 Python 3.10 client로만 연결된다.
  4. CARLA-Air FAQ가 알리는 제한이 있다.
     - 드론을 켠 상태에서는 자동 주행 차를 8대 이하로 두라고 한다. 우리 시험은 최대 44대다.
     - 보행자 AI는 멈춘다.
     - `simSetCameraPose`를 부르면 simulator가 멈춘다.
  5. SimpleFlight 기본 속도 응답(시간 상수 약 4초)은 어차피 실제 쿼드로터를 대표하지 않는다.
- **남는 쓸모.** 드론 몸체가 CARLA 카메라에 보이므로, 나중에 실제 시간 정성 데모를 찍을 때는 쓸 수 있다. 본 실험의 채점에는 쓰지 않는다.

## 4. 대체 경로: CARLA 0.9.16과 자체 동역학

- **simulator.** 지금의 CARLA 0.9.16과 uv 환경(Python 3.12)을 그대로 쓴다. 첫 데모의 시험 목록과 코드도 그대로다.
- **드론 동역학.** 첫 데모 계획 2.3절의 "제한을 지키며 위치를 옮김"을 다음으로 구체화한다.
  - 점질량 모델이다. 최고 속도, 수평·수직 가속도, 방향 회전 속도 제한을 둔다.
  - 속도 명령에 1차 지연을 둔다.
  - 동기 모드 tick마다 적분하므로 재현된다.
- **지연 값.** SimpleFlight 기본값(약 4초)이 아니라 PX4급 쿼드로터의 추종 비행을 대표하는 값으로 정한다. 첫 데모 2단계에서 지연 값 몇 가지로 추종 품질의 민감도를 재고, 사용자와 정한다.
